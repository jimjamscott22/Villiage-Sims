VillageSim — State of the Game Review

Original review: 7 August 2026 · Branch reviewed: main at 9b6895d ("perf: instrument overlay and cull viewport render work", #32)
Graphics & mechanics follow-up: 10 August 2026 — visual browser-demo QA + correctness fixes (seed planting, storm jobs, cargo deposits, selected-villager move orders, demo unlock monotonicity).

Verdict

VillageSim is in genuinely good shape as an engine. The architecture the spec set out — authoritative Rust sim, thin interpolating renderer, data-driven content — is real, is honoured throughout the code, and the whole thing builds and tests clean. Nine of ten milestones are complete and the tenth is nearly there.

It is in noticeably weaker shape as a game. There are six buildings, one crop, and three character traits that have no mechanical effect whatsoever. The systems are built; the content that would make them interesting is not.

The single most important thing to do next is not to finish M10 and not to add content. It is to resolve the fact that the simulation is currently implemented twice — 2,487 lines of Rust in world.rs and 2,404 lines of TypeScript in demoWorld.ts, hand-mirrored, with no automated test that they agree. Every gameplay feature added from here costs double and can silently diverge. Fixing that first makes everything after it cheaper; leaving it makes the content work that the game most needs roughly twice as expensive as it should be.

Findings

Ranked by how much they will cost if left alone.

F1 — The simulation is implemented twice, and nothing checks that the two agree

Severity: high · Category: architecture / maintainability

src/state/demoWorld.ts is 2,404 lines that re-implement the Rust simulation in TypeScript: utility scoring curves, needs decay, hysteresis, job claiming, hauling, production recipes, node regeneration, storm damage, autosave slot rotation, and the building catalog. Every tuning constant is transcribed by hand. They currently match exactly — I diffed them — but that is maintained by discipline alone.

AGENTS.md already documents the hazard ("Mirror every catalog change into DEMO_CATALOG … or the browser-demo drifts from the desktop build"), which is the tell: a known trap guarded only by a note in a file. There is no test that runs the same seed and command sequence through both and compares. Drift will be silent, and it will be discovered as "the demo behaves differently" long after the change that caused it.

The demo has also already diverged in scope: it does not simulate births or deaths at all.

src/state/demoWorld.ts 2404 lines (DemoWorld: full sim reimplementation) src-tauri/src/sim/world.rs 2487 lines of production code (World) src/state/demoWorld.ts:142-174 ~30 tuning constants transcribed from Rust src-tauri/src/sim/utility.rs:32-44, needs.rs:5-7, nodes.rs:7-11 the originals

Three ways out, cheapest first:

  1. Golden-trace conformance test (days). Add a Rust test that runs a fixed seed and scripted command list for N ticks and writes a JSON trace of snapshots to tests/fixtures/. Add a Vitest test that replays the same script through DemoWorld and asserts the traces match. Doesn't remove the duplication, but drift becomes a red CI run instead of a silent bug. Do this regardless of what you pick below.
  2. Compile the sim to WASM (weeks — the real fix). The sim crate has no Tauri dependency in its core; build sim/ to wasm32-unknown-unknown and have the browser transport drive the actual simulation. Deletes ~2,400 lines, makes the demo genuinely faithful, and removes the double cost from every future feature.
  3. Demote the demo to snapshot playback (days). If the demo only exists for headless render testing and screenshots, it doesn't need to simulate — it needs a recorded snapshot stream. Cheapest by far, but gives up interactive browser testing of gameplay.

F2 — World has absorbed the systems that were supposed to live in modules

Severity: high · Category: architecture

The module layout looks right — jobs.rs, crops.rs, economy.rs, pathfind.rs, nodes.rs — but the modules are mostly type definitions and constants. The behaviour is all in World: roughly 110 methods spanning pathfinding, job assignment, hauling logistics, crop tending, production recipes, population dynamics, weather effects, autosave, placement validation and demolition.

Concretely, economy.rs is 138 lines while the hauling and production logic that belongs to it — find_haul_task, deposit_to_storage, take_from_endpoint, nearest_storage_for, tick_produce, tick_haul — sits in world.rs across several hundred lines. Same story for crops and jobs.

This is why F1 hurts so much: there is no seam to test a subsystem in isolation, so the demo has to re-implement the whole thing rather than share a piece of it. It's also the thing that will make adding the content the game needs feel heavy.

src-tauri/src/sim/world.rs:87-2486 impl World — ~110 methods :973 find_haul_task :1584 tick_produce → belongs in economy.rs :2086 tick_crops :2323 tend_water_crops → belongs in crops.rs :2179 refresh_gather_jobs :1287 job_actionable → belongs in jobs.rs src-tauri/src/sim/economy.rs 138 lines (types + constants only)

Suggested approach: don't attempt a big-bang refactor. Extract one subsystem per PR, starting with hauling/production into economy.rs, using a &mut context struct rather than methods on World. The 44 existing world.rs tests are a good safety net for this.

F3 — The tick payload has quietly drifted back toward spec trap #1

Severity: medium · Category: performance

The spec names full-world snapshots as "the single biggest risk in this architecture" and says to viewport-cull from M3 onward. building_views() does cull. Villagers and crops do not — every villager and every crop on the map is serialized into every tick at 20 Hz regardless of where the camera is.

The payload also carries unlocked: Vec<String> — a list of building id strings re-sent 20 times a second even though it changes a handful of times per playthrough. That is spec trap #2 (serializing strings) in miniature, and it is trivially fixable as a bitmask or a sequence number with an on-demand fetch, exactly the pattern chronicle_seq already uses successfully.

Today the map has one crop type and a handful of farms so nothing hurts. At the spec's stated target — 100 villagers, 128×128, farms across the map — crops are the term that grows without bound. Worth noting the frontend measures snapshotBytes in the ?perf=1 overlay but nothing asserts a budget, and there is no tick-duration instrumentation on the Rust side at all, so the spec's ≤5 ms tick budget is currently unmeasured.

src-tauri/src/sim/world.rs:623 tick_snapshot() villagers: self.villagers.iter().map(…) ← every villager, unculled crops: self.crops.iter().map(Crop::view) ← every crop, unculled unlocked: self.unlocked().iter().cloned() ← Vec<String> @ 20 Hz src-tauri/src/sim/world.rs:1859 building_views() ← culls correctly, the model to copy

Fix: reuse the viewport rect from building_views() for villagers and crops; swap unlocked for an unlocked_seq + get_unlocked command. Then add a Rust test asserting a serialized snapshot stays under 20 KB on a densely populated world, and a tick-duration histogram behind a debug flag.

F4 — The two tests the spec calls highest-value don't exist

Severity: medium · Category: testing

§14 of the spec names four test categories. Unit coverage is good (290 tests) and the save round-trip test is present and genuinely rigorous (persist.rs:164 asserts byte-identical re-save). The other two are missing:

  • Full-sim determinism. The spec calls this "the highest-value test in the project". weather_is_deterministic covers the weather function only; nothing runs the same seed and command sequence for N ticks and compares a world hash. The BTreeMap discipline that makes determinism possible is therefore unenforced — a single HashMap added in future passes CI silently.
  • Headless soak. No 10,000-tick no-panic / no-starvation-deadlock run. This is the cheap test that catches economy stalls, and an economy stall is precisely the failure mode a village sim has.

Both are small to write and both directly protect properties the architecture depends on. The determinism test is also a prerequisite for doing F1's golden-trace test properly.

present: src-tauri/src/persist.rs:164 save_round_trip_is_byte_identical_and_continues present: src-tauri/src/sim/weather.rs:119 weather_is_deterministic (weather fn only) missing: same-seed world-hash equality after N ticks missing: 10,000-tick headless soak

F5 — Right-click "move here" ignores which villager you selected

Severity: medium · Category: correctness / UX

Clicking a villager sets selectedVillagerId and populates the villager panel. But the move order doesn't carry that id: moveVillagerTo(x, y) reaches World::order_move, which calls nearest_villager_index_to(x, y) and commands whichever villager is closest to the destination.

So: select Ash, right-click across the map near Briar, and Briar walks. Worse, that call does release_job_at first, so an unrelated villager silently drops their job. This reads as a leftover from M4, when there was only one villager — it survived M7's move to five.

src/render/Canvas.tsx:684 onContextMenu → transport.moveVillagerTo(tile[0], tile[1]) (selectedVillagerIdRef is in scope, not passed) src-tauri/src/sim/world.rs:678 order_move(x, y) → nearest_villager_index_to(x, y)

Fix: thread the selected id through the command and fall back to nearest only when nothing is selected. Small change; touches the IPC signature, both transports and the demo.

F6 — Traits are described to the player but have no mechanical effect

Severity: medium · Category: gameplay honesty

traits.json defines three traits with specific promises: Fast Walker "moves 25% faster", Strong Back "can carry more goods when hauling", Green Thumb "tends crops with extraordinary skill". These strings are shown to the player in VillagerPanel.

No gameplay code reads them. Traits are assigned at spawn, persisted in saves, sent in villager detail, and rendered — and that is the complete extent of it. Movement uses the constant MOVE_SPEED_TILES_PER_SEC unconditionally; hauling uses the constant CARRY_STACK_MAX; crop tending has no trait branch at all.

This is worse than a missing feature, because the UI actively tells the player something untrue. M9 is marked complete on the strength of it. The fix is small — three multipliers at three call sites — and it converts a cosmetic list into the thing that makes individual villagers feel distinct, which is the whole pitch of the game.

src-tauri/data/traits.json 3 traits, each with a stated numeric effect src-tauri/src/sim/world.rs:135,418 assigned round-robin by index/id src-tauri/src/sim/world.rs:674 returned in villager_detail grep -rn "traits" src-tauri/src/sim/ → no read outside assignment + display

F7 — The content is much thinner than the engine that serves it

Severity: low individually, high cumulatively · Category: gameplay

The data-driven content system works well — a building is declared in JSON with footprint, cost, terrain, recipe, storage, jobs and unlock conditions, no code changes needed. It is serving 6 buildings and 1 crop.

  • One crop makes seasons nearly inert. Wheat grows in spring and summer. The clock models four seasons, crops stall in winter, and weather waters them — an entire subsystem whose only expression is "wheat sometimes doesn't grow."
  • Gold is a dead resource. Declared in ResourceTotals, given an icon and a slot in the HUD, and never produced or spent by anything. It is permanently zero on screen.
  • The production chain is one link deep. grain → flour → bread, and that's the economy. Hauling, storage capacity and buffer caps are all built to support more.
  • The unlock tree has almost nothing to gate. With six buildings, progression is over within minutes.

This is the cheapest ratio of effort to felt improvement anywhere in the project — most of it is JSON — but it is exactly the work that F1 doubles, since every catalog entry must be mirrored into DEMO_CATALOG by hand.

F8 — Population growth is a placeholder wearing a milestone's name

Severity: low · Category: gameplay

M9 is "population growth, births/deaths". What's implemented: every 200 ticks (10 seconds of real time), if the villager count is under housing capacity, a villager materialises at the centre of the map. No parents, no age, no gestation, no relationship to which hut has room. The only death is starvation after 300 ticks at zero hunger; nobody ages or dies of anything else.

Population is therefore a step function that rises to the housing cap and then stops forever. A further detail: EXTRA_VILLAGER_NAMES holds 15 names indexed modulo the villager id, so past ~16 villagers the village fills with duplicate names — and traits are assigned by the same modulo, so the same name reliably carries the same trait.

src-tauri/src/sim/world.rs:405 self.clock.tick % 200 == 0 → spawn at map centre src-tauri/src/sim/world.rs:412 name = EXTRA_VILLAGER_NAMES[next_id % 15] src-tauri/src/sim/world.rs:422 trait = traits_pool[next_id % 3] src-tauri/src/sim/agents.rs:84 EXTRA_VILLAGER_NAMES: [&str; 15]

F9 — Documentation overstates what M10 has left, and references tooling that isn't here

Severity: low · Category: documentation

progress.md lists M10's remainder as "camera/interaction polish (hover tooltips, selection highlight)". Selection highlight is already implemented — both for buildings (scene.ts:241) and villagers (scene.ts:368, drawEntities.ts:16-22). What's actually missing is hover tooltips, and there is no pointer-hover inspection path at all.

Separately, AGENTS.md describes deterministic hooks "used by the Playwright smoke flow described in the M1 plan". The hooks (advanceTime, render_game_to_text) do exist and work. The Playwright flow does not — there is no Playwright dependency, no config, and no spec files in the repo. Either build the smoke test or stop referring to it; right now a new contributor will go looking for something that was never committed.

Minor UX gaps in the same area: save/load is hard-wired to slot 1 with a window.confirm() dialog and no way to browse or load the three rotating autosave slots the sim is diligently writing.

Correctness bugs fixed in this follow-up

  • Free TendCrops planting — spend_seed_cost return was ignored; wheat planted with empty grain stockpile. Now gated; bootstrap remains free via manual plant_crop.
  • Storm left production jobs live — damaged mills/bakeries kept Produce jobs and could finish recipes while under construction. Storm now strips site jobs; Produce also requires Complete.
  • Cargo loss — starvation death and player move orders dropped carrying without depositing; both now return goods to the stockpile.
  • Move order ignored selection (F5) — right-click now targets the selected villager; unselected clicks still try nearest-then-next candidates that can path.
  • Demo unlock re-lock — browser-demo replaced unlocked each tick from satisfiedUnlocks(), so demolishing a prereq re-locked buildings. Unlocks are now monotonic like Rust.
  • Villager hit radius — slightly enlarged to reduce missed clicks when selecting sprites.

Still open (mechanics / content)

  • Traits remain cosmetic (F6) — descriptions claim move/haul/tend bonuses the sim never reads.
  • Gold is still dead content; happiness modifiers from the spec are unimplemented.
  • Browser-demo still skips births/deaths; demo saves still omit chronicle/unlocked payloads.
  • Dual-sim duplication (F1) remains the largest structural risk.

Ordered so that each step makes the following ones cheaper. The theme: stop the bleeding on duplication before pouring content in, because content is what the game most needs and duplication is what makes content expensive.

Now — one to two weeks

  1. Add the determinism and soak tests (F4). Same seed + command script → identical world hash after N ticks; and a 10,000-tick headless run asserting no panic and no starvation deadlock. Small, high-leverage, and a prerequisite for step 2.
  2. Add the Rust↔demo conformance test (F1, mitigation). Generate a golden snapshot trace from the Rust sim, commit it as a fixture, replay it through DemoWorld in Vitest. This converts silent drift into a failing build — worth doing even if you later delete the demo entirely.
  3. Fix the move-order bug (F5). Done in the Aug 10 follow-up — selected villager id is threaded through moveVillagerTo, with nearest-pathable fallback when none is selected.
  4. Give traits their effects (F6). Three multipliers at three call sites. Stops the UI making false claims, and is the cheapest gameplay depth available.
  5. Close M10 honestly (F9). Hover tooltips are the real remaining item; add them, correct progress.md, and either commit the Playwright smoke test or remove the reference to it.

Next — the decision that shapes the rest of the project

  1. Decide what the browser demo is for, then commit to it (F1). This is the call to make deliberately rather than by drift:
    • If it exists so gameplay can be tested and demoed headlessly → compile the sim to WASM and delete demoWorld.ts. Highest cost, but it removes the double tax from every feature after it.
    • If it exists so the renderer can be tested headlessly → demote it to snapshot playback and delete the simulation half. Cheap, and honest about scope.
    Either answer is defensible. Maintaining a hand-mirrored second simulation indefinitely is not.
  2. Begin extracting subsystems from World (F2), one per PR, starting with hauling and production into economy.rs. The 44 existing tests make this safe. Do it alongside step 6, not before — the WASM decision affects where the seams should fall.
  3. Cull villagers and crops from the tick payload, and drop the string list (F3), then add the 20 KB budget assertion and Rust-side tick timing so the spec's performance targets are measured rather than assumed.

Later — once a feature costs what it should

  1. Content pass (F7). Three or four more crops with real seasonal spread, a second production chain, buildings worth gating the unlock tree on, and either a use for gold or its removal from the HUD. Mostly JSON — which is precisely why it should follow step 6.
  2. Deepen population (F8). Age, parentage, natural death, and births tied to specific housing. Expand the name pool and randomise trait assignment from the world seed. This is what turns a headcount into a village with a history — and the chronicle system to narrate it is already built and waiting.
  3. Save management UI (F9). A slot browser exposing the three autosaves the sim already writes, replacing the hard-wired slot 1 and the window.confirm.

If only one thing gets done: make the decision in step 6. Everything the game actually needs from here — crops, buildings, chains, traits, population depth — is content, and content is the category the duplication penalises most. The engine is good. It is being asked to carry two copies of itself while the shelves stay empty.

Scope of this review

I read the Rust simulation, the frontend renderer and state layer, the content data files, the build and CI configuration, and the project documentation, and I ran the frontend test suite and production build. I did not run the Rust test suite — the required GTK/WebKit system libraries are absent from this environment and could not be installed — so all statements about Rust behaviour are from reading the source, not from execution. I did not run the desktop app, which needs a display, and I did not profile at the spec's stated load of 100 villagers; the performance observations in F3 are analytical, drawn from what the snapshot code serializes rather than from measurement.
